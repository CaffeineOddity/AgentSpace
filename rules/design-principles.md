# 设计模式与软件原则

## 规范驱动开发（Spec-Driven Development, SDD）

- 遵循规范驱动开发：需求先落 spec，代码随 spec 走，spec 与代码始终一致。
- 每个需求点在项目目录下创建 `docs/specs/<需求名>.md` 规范文档，作为该需求
  的唯一事实来源（single source of truth）。
- spec 文档须记录：需求背景与目标、接口/数据结构设计、行为约定、验收标准、
  已知边界与不做项；以「当前状态」描述，不是变更日志。
- 代码变更与 spec 同步：
  - **新增功能**：先写（或更新）对应 spec，再实现代码。
  - **调整需求/迭代**：先改 spec，再改代码，使代码贴合更新后的 spec。
  - **删除功能**：先删代码，再删对应 spec（或标注废弃），不留孤儿 spec。
- 改代码前先读对应 spec；spec 与代码出现矛盾时，以 spec 为准并据其修正代码，
  若发现 spec 本身有误则先修 spec 再改代码，二者不得长期背离。
- spec 命名简短、kebab-case、按需求点一文件；`docs/specs/` 下不建子目录除非需求
  明显分层（如多模块各自一组）。
- spec 只描述「做什么、为什么、约束是什么」，不贴大段实现代码；实现细节留在
  代码与 docstring 里，spec 引用其路径即可，避免重复。
- spec 行文简洁、不啰嗦：直说结论与约束，删掉铺垫与复述；
  跨 spec 需要同一信息时用引用（如「见 docs/specs/xxx.md 的某节」），不复制内容。

## 新需求模块组织

新增一个完整需求点时，实现不得松散地散落到既有文件/目录中。
应新开独立目录承载该需求的全部实现，保持高内聚；对外只暴露接口，
在合适的组合点注入/调用，而不是把逻辑直接写进既有模块内部。

- **完整需求点**：有独立 spec、独立业务边界的新功能（见上方 SDD）。
  小修小补、对既有模块的局部修正不在此列，仍按最小 diff 改原处。
- **独立目录**：按需求命名（kebab-case），目录内放该需求自己的类型、
  逻辑、适配器；不要把新需求的文件塞进无关模块旁「顺便放下」。
- **高内聚**：该需求的代码只因该需求而变化；目录外不得出现该需求的
  实现细节副本。
- **接口 + 注入**：目录对外提供清晰接口（函数/类型/插件注册点），
  调用方只在组合根、入口、配置等组合点注入或挂接；禁止深入目录内部抓实现。
- **禁止**：为赶工把新逻辑插入既有 God Function / 既有文件末尾；
  禁止跨多个无关模块同时新增同一需求的碎片实现（Shotgun Surgery）。

## 适用原则优先级

面对设计决策时，按以下顺序权衡（从最普适到最具体），避免教条式套用：

1. **KISS** — 最简单的能工作的方案优先。简单方案够用时不引入额外结构。
2. **YAGNI** — 不为猜想的未来需求提前抽象。只在确有第二个使用方时再抽取通用结构。
3. **DRY** — 同一逻辑只出现一次，通过抽取函数/模块/常量复用；
   但仅当重复是真正的「同一份逻辑」时才抽取，避免把偶发相似误判为重复。
4. **CRP（组合复用原则）** — 优先组合而非继承；通过依赖接口/可注入依赖来复用行为。
5. **LoD（迪米特法则）** — 一个对象只跟它直接依赖的对象通信，
   不通过 `a.b.c.method()` 链式深入他人内部，不把调用方不需要的实现细节暴露出去。

## SOLID（面向对象设计）

仅用于 OOP 类（连接器、外部系统接口）。函数式代码不必强行套用。

- **S（SRP，单一职责）**：一个类/函数只对一个原因变化负责。类的大小以内聚的单一职责为准。
- **O（OCP，开闭原则）**：对扩展开放、对修改关闭。新增行为通过新增子类/策略/参数化配置实现，而非改写已有方法。
- **L（LSP，里氏替换）**：子类必须能替换父类且不破坏行为约定。重写方法不得改变父类的不变量、前置/后置条件。
- **I（ISP，接口隔离）**：客户端不应依赖它不使用的方法。接口按调用方需求拆分，避免胖接口。
- **D（DIP，依赖倒置）**：依赖抽象而非具体实现。通过注入依赖（构造器/参数/配置）解耦，配合 CRP 的组合复用。

## 设计模式选用指引

模式是命名了的常见问题解法，不是目标本身。**先识别问题，再判断模式是否匹配；不要为了用模式而用模式。**

| 模式 | 适用场景 | 反模式信号 |
|---|---|---|
| Factory / Abstract Factory | 对象创建逻辑复杂、需按类型/参数分派 | 只需一次 `new`/构造函数调用时 |
| Strategy | 同一算法有多种可替换实现、运行时可选 | 只有一种实现，或分支可用简单 `if/elif` 表达时 |
| Adapter | 接入外部系统，统一对方协议到本方接口 | 双方接口本就一致 |
| Facade | 为复杂子系统提供精简入口 | 子系统本身简单 |
| Repository / DAO | 隔离数据访问、便于替换存储实现 | 只有一种存储，且直接查询更清晰 |
| Observer / 事件 | 一对多状态通知、解耦触发方与订阅方 | 单向同步调用即可满足 |
| Template Method | 算法骨架固定、步骤由子类定制 | 骨架也在变，或可用组合代替继承时 |
| Decorator | 在不改原对象下叠加职责 | 可用简单函数包装/组合代替 |

**优先组合（CRP）而非继承**：能用「持有并调用」表达的关系，不要用「is-a 继承」表达。函数式场景用高阶函数/依赖注入实现同样的复用。

## 反模式（避免）

- **God Object / God Function**：一个类/函数承担过多职责（SRP 违背）。
- **Shotgun Surgery**：一次需求变化散落到多个类/函数修改（DRY 违背）。
- **Feature Envy**：函数过度访问他人内部数据而非自己的数据。
- **Law of Demeter 违背**：`a.b().c().doX()` 式深链调用。
- **Premature Abstraction**：YAGNI 违背，先写具体实现，出现第二使用方再抽象。

## 实操落地

- 写新代码前先检查「代码风格」（纯函数、严格类型、单职责函数）与「工作流」（改动最小聚焦）。
- 判断一个「通用结构」是否该建，问自己：是否有第二个真实使用方？若没有 → YAGNI，直接写具体实现。
- 抽象命名用「它解决什么」而非「它是什么」，避免以技术手段命名的空洞抽象。
- 涉及外部系统时，用接口 + 注入实现解耦。
