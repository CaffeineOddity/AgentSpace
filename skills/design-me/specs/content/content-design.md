# 内容设计规范

> 本文件是 UI 文案与内容设计的唯一事实来源。视觉规范见各端 spec，本 spec 覆盖界面中的文字：按钮、标签、错误信息、空状态文案、表单提示、成功反馈、tooltip。

## 设计目标

让界面中的每一段文字都清晰、准确、有帮助。核心矛盾是「简洁」与「完整」的平衡--太短用户看不懂，太长用户不看。内容设计的标准是：用户读完文字后知道发生了什么、该做什么，不产生疑问。

内容设计是设计的一部分，不是后期填充。按钮叫「提交」还是「保存」、错误提示写「出错了」还是「网络连接失败，请检查后重试」，这些决策直接影响可用性。视觉再好，文案差，用户一样难用。

## 文案原则

| 原则 | 说明 | 反例 |
|------|------|------|
| 清晰优先 | 用用户能懂的话，不用技术术语 | 「会话已终止」→ 「登录已过期，请重新登录」 |
| 动词开头 | 操作类文案用动词，告诉用户能做什么 | 「确定」「取消」→ 「保存」「放弃修改」 |
| 说原因给出路 | 错误不只说错了，要说为什么和怎么办 | 「操作失败」→ 「文件超过 10MB，请压缩后重传」 |
| 简洁但不省信息 | 删掉废话但保留关键信息 | 「您的操作已经成功完成」→ 「已保存」 |
| 一致用词 | 同一动作全产品用同一个词 | 不混用「删除/移除/清除」表达同一操作 |
| 语气匹配场景 | 成功用鼓励，错误用克制，不用感叹号 | 错误不写「哎呀出错了！」 |

## 操作流程

### C1. 按钮文案

按钮是最高频的 UI 文案。规则：

| 类型 | 规则 | 示例 |
|------|------|------|
| 主操作 | 动词 + 对象，≤ 4 字 | 「创建项目」「提交订单」 |
| 次操作 | 动词，≤ 2 字 | 「取消」「返回」 |
| 破坏性操作 | 明确后果 | 「删除文件」「清空全部」 |
| 加载中 | 状态 + 进行时 | 「保存中...」「提交中...」 |
| 完成 | 过去时或确认 | 「已保存」「完成」 |

- 禁用「确定」「OK」「好的」--这些词不告诉用户按钮做了什么
- 破坏性操作不用「确认」做二次确认按钮，用具体动作（「删除」「清空」）
- 按钮文案全产品一致：同一操作用同一个动词

### C2. 表单标签与提示

| 元素 | 规则 | 示例 |
|------|------|------|
| 标签 | 名词，简洁，1-3 字 | 「邮箱」「密码」「收货地址」 |
| 占位符 | 示范输入格式，不替代标签 | placeholder：「name@example.com」 |
| 辅助提示 | 说明格式要求或限制 | 「密码须 8-20 位，含字母和数字」 |
| 必填标记 | 用 `*` 标注，说明含义 | 「邮箱 *」+ 底注「* 为必填项」 |

- 占位符不替代标签（占位符输入后消失，用户失去上下文）
- 辅助提示常驻显示，不只在出错时出现
- 标签用用户语言，不用数据库字段名（「手机号」不用「phoneNumber」）

### C3. 错误信息

错误信息是最影响用户体验的文案。结构：**发生了什么 + 为什么 + 怎么办**。

| 场景 | 差文案 | 好文案 |
|------|--------|--------|
| 网络错误 | 「网络错误」 | 「网络连接失败，请检查网络后重试」 |
| 必填空 | 「不能为空」 | 「请输入邮箱地址」 |
| 格式错误 | 「格式不正确」 | 「邮箱格式应为 name@example.com」 |
| 超限 | 「操作失败」 | 「文件超过 10MB，请压缩后重传」 |
| 权限不足 | 「无权限」 | 「此功能需要管理员权限，请联系管理员」 |
| 重复提交 | 「错误」 | 「该内容已存在，请直接编辑」 |

规则：
- 说明具体原因，不用「出错了」「操作失败」「错误」等无信息文案
- 给出可操作的解决路径（重试/检查/联系/修改）
- 不指责用户（「您输入错误」-> 「邮箱格式应为...」）
- 错误信息出现在相关字段旁，不堆在页面顶部

### C4. 空状态文案

空状态不是错误，是正常状态。文案结构：**现状说明 + 行动引导**。

| 场景 | 差文案 | 好文案 |
|------|--------|--------|
| 列表无数据 | 「暂无数据」 | 「还没有项目，点击创建第一个」 |
| 搜索无结果 | 「无搜索结果」 | 「未找到「xxx」相关结果，试试其他关键词」 |
| 无权限 | 「无权限」 | 「暂无访问权限，申请权限后可查看」 |
| 新用户引导 | 「欢迎使用」 | 「开始创建你的第一个任务吧」 |

规则：
- 不用「暂无数据」「无内容」「空」--这些不引导用户行动
- 给出明确的下一步操作（按钮或链接）
- 语气积极，不让用户觉得出了问题

### C5. 成功与确认反馈

| 类型 | 规则 | 示例 |
|------|------|------|
| 操作成功 | 过去时，确认完成 | 「已保存」「已发送」「订单已创建」 |
| 批量操作 | 说明数量 | 「已删除 3 个文件」「已导出 120 条记录」 |
| 可撤销 | 提示撤销入口 | 「已删除，撤销」 |
| 进度 | 进行时 + 百分比 | 「正在上传 45%」 |
| 确认弹窗 | 说明后果 + 两个操作 | 「删除后不可恢复，删除 / 取消」 |

- 成功反馈用 Toast/Snackbar，不用模态弹窗（不打断用户）
- 破坏性操作用确认弹窗，文案明确后果
- 可撤销操作优先提供「撤销」而非二次确认；**「撤销」必须是可点击的真入口**（文本提及但不可点=摆拍），可撤销 Toast 停留 ≥5 秒（阅读+决策时间），不可撤销 2-3 秒即可

### C6. 导航与标题

| 元素 | 规则 | 示例 |
|------|------|------|
| 页面标题 | 名词，简洁，1-4 字 | 「设置」「订单详情」「个人中心」 |
| Tab 标签 | 名词或动名词，≤ 2 字 | 「首页」「发现」「消息」「我的」 |
| 模态标题 | 说明模态目的 | 「新建项目」「编辑资料」 |
| 章节标题 | 概括内容 | 「基本信息」「收货地址」 |

- Tab 标签全产品风格一致（要么全名词，要么全动名词）
- 页面标题与导航标签一致（Tab 叫「我的」，页面标题也叫「我的」，不叫「个人中心」）

### C7. tooltip 与辅助说明

- tooltip 用于解释图标按钮或复杂字段的含义
- 文案 ≤ 15 字，一句话
- 不在 tooltip 里放重要信息（移动端无 hover，tooltip 不显示）
- 复杂说明用常驻辅助文字，不用 tooltip

## 一致性管理

全产品的文案用词须一致。建立术语表：

| 概念 | 统一用词 | 禁用词 |
|------|---------|--------|
| 删除 | 删除 | 移除、清除、丢弃 |
| 确认 | 确认 | 确定、OK、好的 |
| 提交 | 提交 | 上传（非文件场景）、发送（非消息场景） |
| 用户 | 用户 | 客户、会员（非会员制产品） |
| 账号 | 账号 | 账户、ID、用户名（非登录名场景） |
| 订阅 | 订阅 | 开通（付费场景）、购买（非商品场景） |
| 取消订阅 | 取消订阅 | 退订、关闭会员 |

- 术语表随产品迭代维护，新增功能时检查用词一致性
- 术语表与 `specs/design-system` 的 Token 一样是单一事实来源——**须有结构化载体文件**（如 `terms.json`：概念/统一用词/禁用词/场景），HTML 表格只是可视化展示；全仓文案一致性检查以载体文件驱动

## 可审阅文案集 HTML

产出单页 HTML，将全部 UI 文案 + 术语表可视化供一致性审阅：

- 按页面/功能区分组，每组一个区块
- 每条文案一格：文案原文 + 类型（按钮/标签/错误/空状态/成功/tooltip）+ 所在位置
- 术语表单独一个区块，展示概念/统一用词/禁用词对照
- 弹出式审阅（见 `specs/review`）：每条文案有 [+] 按钮，点击弹窗写反馈 + 快捷标记
- 支持导出 Markdown/JSON 给 AI 修改，保留上一轮反馈对比
- 用于独立内容设计任务或项目流程中的文案审阅检查点

文案集 HTML 定稿后，文案直接进入各端 UI 原型（Phase 4），术语表纳入 `specs/design-system` 资产管理。

## 验收标准

- [ ] 按钮文案用动词，无「确定/OK/好的」
- [ ] 破坏性操作按钮文案明确后果
- [ ] 表单标签 + 占位符 + 辅助提示三层结构完整
- [ ] 错误信息含「原因 + 解决路径」
- [ ] 无「出错了/操作失败/错误」等无信息文案
- [ ] 空状态有行动引导
- [ ] 成功反馈用 Toast，不用模态
- [ ] 破坏性操作有确认弹窗
- [ ] Tab 标签风格一致
- [ ] 术语表已建立，同概念用词全产品一致
- [ ] tooltip 文案 ≤ 15 字，不含重要信息
- [ ] 订阅/付费场景：用「订阅/升级/取消订阅」，不用「开通/购买/退订」（术语表场景化条目示范：同一概念在付费语境的禁用词须显式列出）

## 边界与不做项

- 不负责营销文案与品牌口号（见 `specs/brand`）
- 不负责长文内容撰写（文章正文、帮助文档）
- 视觉规范见各端 spec（`specs/web`、`specs/mobile`）
- 文案的多语言翻译见国际化设计（本 spec 定义中文基线，翻译规则另定）
- 术语表归属 `specs/design-system` 的资产管理
